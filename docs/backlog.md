# Backlog

Findings from architecture reviews. Each entry is one line: what to do, in which file, and whether it is a suggestion or a warning.

## From run 5 (show the most recent run's outcome and reason)

- **Suggestion** — `viewer.py`: the rule "a run has ended when its outcome is non-empty" lives in `_render_latest` and in comments on `LatestRun`, so any second consumer must re-derive it; give `LatestRun` an `ended` property and have the presentation ask that instead of comparing to `""`. (Ideal: well-defined layers.)
- **Suggestion** — `viewer.py`: `render_page` calls `db_path()` to build the "count unavailable" message, so the presentation layer reads the environment and cannot be rendered from its arguments alone; pass the path (or the whole unavailable message) in from the data layer. (Ideal: well-defined layers.)
- **Suggestion** — `tests/test_viewer.py`: the not-ended, empty-reason and escaping rules are each asserted at three levels (`read_page_data`, `render_page`, HTTP), so a change to one rule must be made in three sections; keep the rule cases at the `render_page` level and let the HTTP tests assert only that the body equals `render_page(read_page_data())` plus freshness between requests. (Ideal: absorb change over time.)

## From run 6 (one page-data value, read once, that says what could not be read)

- **Suggestion** — `viewer.py`: `UNREADABLE` carries no cause, so `read_page_data` turns every `sqlite3.Error` (missing file, missing table, missing column, a busy or locked database) into the same marker and `_render_latest` and `render_page` each hard-code a guessed cause ("could not read outcome and reason from the runs table" is shown even when the file does not exist); have the data layer return the reason with the marker (for example a small `Unreadable(reason)` value holding the SQLite message and the path) and have the presentation print it, which also settles the `db_path()` suggestion above. (Ideal: explicit interfaces between layers.)
- **Suggestion** — `viewer.py`: `read_page_data` writes "run one statement, convert the row, or give `UNREADABLE` on `sqlite3.Error`" out in full for each fact, which is cheaper than a helper at two facts but means a third fact copies the block and its union type again; when the next fact is added, move the pattern into one helper that takes the connection, the SQL and a row converter, and leave it as it is until then. (Ideal: absorb change over time.)

## From run 7 (a page at /runs listing every run)

- **Warning** — `tests/test_viewer.py`: `test_viewer_imports_only_the_standard_library` rejects any import that is not in `sys.stdlib_module_names`, which also rejects a sibling module, so the three layers can only ever be a naming convention inside one growing `viewer.py` and nothing stops a `render_*` function calling `db_path()` or `sqlite3`; change the test to allow imports of this codebase's own modules (and check them for standard-library-only imports too) so the layers can become modules when the next page arrives. (Ideal: well-defined layers with explicit interfaces.)
- **Suggestion** — `viewer.py`: the condition named in the run 6 entry above has now been met, because `read_runs_page_data` is a third copy of "connect, run a statement, convert rows, or give `UNREADABLE` on `sqlite3.Error`" and already differs from `read_page_data` in small ways (no `BEGIN`, a different `try` shape); move the pattern into the one helper that entry describes before a fourth read is written. (Ideal: absorb change over time.)
- **Suggestion** — `viewer.py`: a run is now modelled twice, as `LatestRun` and as `RunSummary`, and the rule "ended means the outcome is non-empty" is stated in `RunSummary.ended` and again as `latest.outcome == ""` in `_render_latest`; make the home page's latest run a `RunSummary` (adding `reason` to it) or have both share one `ended` rule, so that a change such as treating a dead driver as stopped (run-store guarantee 6) is made once and both pages agree. (Ideal: well-defined layers.)
- **Suggestion** — `viewer.py`: `_PAGES` maps an exact path to a function of no arguments that returns HTML, and `_Handler.do_GET` always answers 200, so the likely next page, one run at `/runs/<id>`, cannot be added as an entry because it needs a value from the path and a 404 for an unknown id; when that page is asked for, change the entry's shape to a function that takes the path's parts and returns a status with the body, and leave the mapping as it is until then. (Ideal: absorb change over time.)
- **Suggestion** — `viewer.py`: `read_runs_page_data` fetches the full `request` text of every run on every request although the page shows ten words of each, so the cost of one page view grows with the whole history and with the length of requests; when the table grows large, either select a bounded prefix (`substr(request, 1, N)`) or add paging in the data layer, with `RunsPageData` saying which slice it holds. (Ideal: absorb change over time.)
- **Suggestion** — `viewer.py`: `_parse_time` turns any timestamp that is not exactly `%Y-%m-%dT%H:%M:%SZ` into `None`, so if the factory ever writes fractional seconds or a numeric offset every row silently reads "unknown" for created and duration with nothing saying why; accept the other ISO 8601 UTC forms there, since that function is the one place the stored format is known. (Ideal: explicit interfaces between layers.)
- **Suggestion** — `tests/test_viewer.py`: the tests now build the `runs` table two ways, the loose `make_db`/`make_outcome_db` tables the home-page tests use and the `RUNS_DDL` copied by hand from `docs/run-store.md`, so a schema change must be made in the document, in `RUNS_DDL` and in the loose builders, and the home page is mostly tested against a table the factory never makes; build every test database from `RUNS_DDL` and keep the loose tables only for the "column missing" cases. (Ideal: absorb change over time.)
- **Suggestion** — `tests/test_viewer.py`: the run 5 entry about rules asserted at three levels now applies to `/runs` as well, where status, ordering, escaping, unreadable databases and read-only behaviour are each asserted for `read_runs_page_data`, `render_runs_page` and `GET /runs`, in about 1,600 lines for about 150 lines of code; keep each rule at the level that owns it and let the HTTP tests cover routing, headers and the body equalling `render_runs_page(read_runs_page_data())`. (Ideal: absorb change over time.)

## From run 11 (a page at /runs/<id>/steps/<step id> showing one step in full)

- **Suggestion** — `viewer.py`: `_read_one_and_its_rows` answers the run 7 helper entry for two of the four readers only, and its shape (exactly one row, then exactly one set of rows, both taking the same `params`) is the shape of the two pages that exist rather than of reading, so `read_page_data` and `read_runs_page_data` still hand-write connect/`BEGIN`/close and a page needing a third statement (a step's questions, a run's events) must copy the block again; put the lower piece underneath it, one context manager that opens read-only, begins, closes once and hands out a `fetch(sql, params)` that gives rows or `UNREADABLE`, and write all four readers on that. (Ideal: most functionality for least code; absorb change over time.)
- **Suggestion** — `viewer.py`: `read_step_page_data` reads `asked` and `produced` as `step[8]` and `step[9]`, which is right only while `_STEP_COLUMNS` names exactly eight columns, so adding a column to the summary (`kind`, `failure`) silently moves both; set `conn.row_factory = sqlite3.Row` in `_connect` and read columns by name in every converter, which also removes the "in the order it takes them" coupling between `_STEP_COLUMNS` and `_step_summary`. (Ideal: explicit interfaces.)
- **Suggestion** — `viewer.py`: this change gave steps one `_STEP_COLUMNS` and one `_step_summary` but left runs without the pair, so the six `RunSummary` columns and their conversion are still written out in both `read_runs_page_data` and `read_run_page_data`; add `_RUN_COLUMNS` and `_run_summary(row)` beside the step ones so a new run column is added in one place. (Ideal: most functionality for least code.)
- **Suggestion** — `viewer.py`: the line `<p id="X-unavailable">X unavailable: could not read Y</p>` is now written out eight times and the `<table>`/`<thead>`/`<tbody>` scaffold four times, while the tests already state each once (`UNAVAILABLE_LINE`, `TABLE_CLOSE`); add `_unavailable(id, what, source)` and `_table(id, headings, rows)` to the presentation layer and have every page use them, so the run 6 change of printing a cause with the marker is made in one function instead of eight. (Ideal: most functionality for least code.)
- **Suggestion** — `viewer.py`: `read_step_page_data` fetches every event of the step with no limit, and an agent step writes one event per tool use and per piece of agent text, so one page view grows with the step's length inside a read transaction that run-store.md says must be short; when steps grow long, page the events with the documented cursor (`id > ? ORDER BY id LIMIT 500`) and have `StepPageData` say which slice it holds. (Ideal: absorb change over time.)
- **Suggestion** — `viewer.py`: the id pattern `[1-9][0-9]{0,17}` is now written three times in `_ROUTES` and the path `/runs/{run_id}/steps/{step.id}` is built by hand in `_render_step_row` apart from the pattern that must match it, so a change to either the id rule or the URL shape has to be made in places nothing ties together; name the pattern once (`_ID`) and put a `_step_path(run_id, step_id)` next to `_ROUTES` for the presentation layer to call. (Ideal: explicit interfaces between layers.)
- **Suggestion** — `tests/test_viewer.py`: `FAILING_STATEMENTS` picks its readers by position (`READERS[2].values[0]`, `READERS[3].values[0]`), so inserting or reordering a reader silently points those cases at a different function; name each reader lambda once as a constant and build both tables from the names. (Ideal: absorb change over time.)
